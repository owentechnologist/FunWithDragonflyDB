# go-router-service: no-Lua microservice router

A third, architecturally distinct implementation of the `(fqdn1, port, fqdn2)
-> rule` matcher, alongside the Python+Lua original (`fqdn_router.py`) and its
Go port (`go-benchmark/`). Both of those keep the matching logic *inside*
Dragonfly as a Lua script (`EVALSHA`). This one keeps Dragonfly's job down to
plain `HMGET`/`HSET` and moves candidate generation, key construction, scope
filtering, and specificity ranking into a Go microservice tier instead.

```
pure client (any language, another process)
      |  gRPC Lookup(fqdn1, port, fqdn2, mode)
      v
routerd  (stateless, N replicas)
      |  one pipelined batch of HMGETs, one round trip
      v
Dragonfly  (only ever answers HMGET/HSET)
```

A pure client never sees Redis, hash tags, or wildcard ranking — it sends the
exact equivalent of `store.Lookup("probe.host7.corp3.dragonfly42.com", 443,
"probe.dest42.example.com", MultiLevel)` over gRPC and gets back a match or a
miss. Every `routerd` instance is fully stateless (no local cache, no
in-memory rule state), so N instances behind a load balancer add lookup
capacity linearly, bounded only by Dragonfly itself — that's the scaling bet
this architecture is testing.

## Layout

- `pattern.go`, `layout.go`, `rulemix.go` — copied unchanged from
  `go-benchmark/`. Pure domain logic (candidate generation, hash tagging,
  scope filtering, specificity ranking), no I/O, architecture-agnostic.
- `store.go` — `NoScriptRuleStore`. `Put`/`PutMany`/`Delete` are byte-for-byte
  the same as `go-benchmark`'s `RuleStore`, writing the exact same physical
  key layout (`r:{ns:<tag>}:<pattern>:<port>` HASH), so this store reads data
  `go-benchmark` already wrote. `Lookup` never loads or evaluates Lua: it
  pipelines one `HMGET` per fqdn1 candidate key in a single round trip, then
  scans the flattened `(aCandidates, bCandidates)` space — already returned
  in ascending, most-specific-first rank order by `candidates()` — for the
  first unblocked hit. That's the same `(rank1, rank2)`-minimum semantics the
  Lua script's per-group loop implements, collapsed into one flat loop since
  there's no `EVALSHA` slot boundary forcing candidates into hash-tag groups
  first.
- `proto/router.proto` — the wire contract: one RPC, `Lookup`.
- `server.go` — gRPC service wrapping `NoScriptRuleStore.Lookup`.
- `cmd/routerd/main.go` — the server binary.
- `golden_test.go` — cross-checks this store against the same fixed
  rule/query set `go-benchmark/golden_test.go` uses (generated by
  `../go-benchmark/crosscheck_python.py`), proving it agrees with the
  Python/Lua original on every match and writes an identical physical key
  set, before any performance number is trusted.

## Running it

```
go build -o routerd ./cmd/routerd
./routerd -uri redis://localhost:6379/0 -namespace bench -num-buckets 16 -listen :9090
```

`-namespace` and `-num-buckets` must match whatever wrote the data. Run
several instances on different ports (or behind a load balancer) to test the
fleet.

## Verifying correctness

```
python3 ../go-benchmark/crosscheck_python.py /tmp/crosscheck.json
FQDN_GOLDEN=/tmp/crosscheck.json go test -run TestGoldenCrossCheckAgainstPython -v
```

## Comparing against the other two architectures

`go-benchmark`'s benchmark CLI has a `-target` flag: `direct` (arch 2, today's
default) or `grpc=host:port[,host:port,...]` (arch 3, round-robins across the
given `routerd` addresses). The write phase always goes straight to
Dragonfly — `routerd` has no `Put` RPC by design — so write once, then point
the same query phase at either architecture:

```
# write the dataset once (arch 2's own write path)
./benchmark -num-rules 1000000 -num-buckets 16 -db 0

# arch 2: query the data directly
./benchmark -num-rules 1000000 -num-queries 200000 -no-flush -db 0 -target direct

# arch 3: query the same data through N routerd instances
./benchmark -num-rules 1000000 -num-queries 200000 -no-flush -db 0 \
  -target grpc=router1:9090,router2:9090,router3:9090
```

Because both runs read the identical dataset (no PRNG-driven layout to keep
in sync, unlike comparing against `benchmark.py`'s own write phase — see
`go-benchmark/README.md`), the only variable across the two reports is the
implementation. `benchmark.py --no-flush` against the same dataset gives
arch 1's numbers for the same comparison, once its own PRNG-based layout is
sidestepped by not using its write phase.

## Bottleneck hypotheses / pros and cons

| | Arch 1: Python + Lua | Arch 2: Go + Lua | Arch 3: Go microservice, no Lua |
|---|---|---|---|
| Client compute ceiling | GIL-bound (measured: 2 processes doubled throughput at fixed concurrency) | none (goroutines) | none (goroutines), and scales by adding stateless replicas independent of caller count |
| Network round trips / lookup | 1 (pipelined `EVALSHA`s, ≤3 groups) | 1 (same) | 1 `HMGET` pipeline + the extra pure-client -> routerd hop |
| Dragonfly-side commands / lookup | ≤3 | ≤3 | up to `len(aCandidates)` (typically 3-6 for real-world label depth, worst case ~21 at `maxLabels`) |
| Response payload / lookup | O(1) — one `{i,j,ruleid}` tuple | O(1), same | O(aCandidates × bCandidates) field values, mostly nil — no server-side early exit once commands are pipelined eagerly |
| Dragonfly CPU | Lua interpreter + shard-thread time | same | plain `HMGET` (cheaper per op, no interpreter), but more ops dispatched |
| Coupling | caller needs a direct Redis connection + `EVAL` rights | same | caller needs only host:port + 3 scalars; Dragonfly credentials/topology live only in `routerd` |
| Ops surface | script load/version/`NOSCRIPT` handling on restart | same | no script lifecycle; works against Redis-compatible tiers that restrict `EVAL`; adds a fleet to deploy/scale/monitor |
| Code / testability | matching logic partly in a Lua string | same | plain Go; the winner-search loop is simpler than arch 2's (no per-group/cross-group split needed) |

The central, falsifiable question this architecture exists to answer: whether
the O(1) -> O(n×m) blowup in Dragonfly-side commands and response bytes
(traded for zero Lua, decoupled callers, and independently scalable compute)
is a net win or a net loss at realistic query concurrency, and whether it's
the extra network hop or the extra payload that dominates p99 once measured.

Not built here, and deliberately out of scope for this first cut: cross-call
request coalescing (batching multiple concurrently-arriving `Lookup` RPCs'
`HMGET`s into one shared Dragonfly pipeline). It's a real lever for "gang up
on Dragonfly" harder, but it's itself something to measure against a
per-call-pipelining baseline, not something to assume is a win and bake in
before that baseline exists.
